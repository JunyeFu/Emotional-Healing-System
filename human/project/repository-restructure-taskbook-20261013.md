# SRP GitHub 与本地目录改造任务书

> 版本：v1.0；编制日期：2026-10-13。
> 状态：W1-W5已实施并验收。目录、展示与开发入口已完成；完整源码与GitHub默认首页均已发布并实际回读。
> 本任务是仓库组织专项，不新增或改写现有71项业务任务状态；不改变研究设计、运行合同及原签收范围。

## 一、目标与判断

将同一套项目文件组织成两种顺畅的使用方式：对外能够快速认识项目，对内能够定位源码、运行开发验证并继续协作。GitHub与本地使用同一个版本化目录，不建立两套手工维护的项目副本。

建议采用 **“展示与开发入口重构 + 有依据的有限归位”**。保留当前 `human/`、`agent/` 物理骨架，改变其入口职责；不立即把全部工程再次搬到 `docs/`、`src/`、`apps/`。

理由：现有根目录已经完成19项迁移，71个任务包、领取快照、工程及验证工具均依赖现有路径。当前最明显的障碍是入口内容顺序、职责混淆和版本导航，而不是目录名本身。仅换一套目录名，不能解决“哪个版本能用、源码在哪里、如何接着做”。

| 方案 | 收益 | 代价 | 决定 |
|---|---|---|---|
| 仅缩短首页 | 立即改善第一印象 | 新人仍需深入任务包寻找开发入口 | 不单独采用 |
| 入口重构、明确文件归属、有限归位 | 同时改善介绍、查找和继续开发；保持现有工程可用 | 需整理当前权威与历史材料、修正生成器入口 | 本任务推荐范围 |
| 全量改为 `docs/src/apps/tests` | 顶层命名更符合常见软件仓库 | 大量路径、脚本、Unity引用、任务快照及分发材料需迁移 | 本轮不采用；只有明确开发收益时另立迁移任务 |

### 1.1 完成标准

| 使用者 | 应完成的实际动作 | 验收目标 |
|---|---|---|
| 首次访问者 | 说清项目服务谁、体验是什么、研究什么、当前做到哪里 | 浏览首页和项目概览，3分钟内完成；不先读任务编号 |
| 想看成果的人 | 找到一项当前实物或预演，以及其版本与证明范围 | 从首页不超过2次跳转；不能把设计稿当运行截图 |
| 新开发者 | 找到目标模块源码、环境要求及一条无硬件定向验证命令 | 从首页到对应操作说明不超过2次跳转；已具备依赖时30分钟内完成验证 |
| 接任务的成员 | 找到当前可领取任务、输入、交付位置及验收入口 | 从首页不超过2次跳转到任务索引或领取入口 |
| 研究审阅者 | 区分当前设计、原签收、真实证据与尚未完成事项 | 从项目概览进入同一权威来源，不依赖日志拼接事实 |

“3分钟/30分钟”是后续走查目标，不是本轮已经取得的用户测试结果。新装大型工具的下载时间不计入开发验证耗时，但安装前提必须写明。

## 二、现状与需要解决的问题

核查范围：本地 `D:\Agent\srp` 的首页、项目概览、模块与运行入口、任务审阅导航、依赖和Git规则；GitHub仓库元信息及默认分支首页。未逐一审计全部源码和二进制资产。

| 已观察事实 | 对使用者的影响 | 本任务处理 |
|---|---|---|
| [根README](../../README.md)在项目简介之前放入大量迁移记录、设计修订和71项任务链接 | 新读者先接触内部编号，难以迅速理解项目 | 项目介绍前置；详细任务和迁移信息移交专属索引 |
| [人类入口](../README.md)主要是PDF生成说明与逐包审阅表 | “human”并未实际承担新读者入口 | 改为按阅读目的分流；完整任务表移至任务索引 |
| [模块入口](../../agent/modules/README.md)优先展示旧 `main.py` 模拟链，后面才列当前模块 | 开发者容易从历史原型开始 | 当前源码与验证前置；旧快速启动独立标明历史用途 |
| 模块入口写M06为TD、M07为Unity，而[项目模块地图](PROJECT_MODULES.md)写M06为Unity、M07为TD | 同一编号指向不同职责 | 文档以模块地图为基准核对；不顺带重编号运行字段或冻结合同 |
| [当前运行入口](../../agent/runtime/README.md)有职责和任务链接，但缺少面向新人的完整开发步骤 | 不清楚先装什么、先跑哪项、什么输出算成功 | 增补可实际执行的分模块开发路径，不虚构统一启动器 |
| 源码位于 `agent/modules/`，任务执行工具分布在 `agent/tasks/*/execution/` | 只看目录名无法区分应用实现、任务工具和证据生成器 | 开发指南列明源码权威及辅助工具位置；只对确认错放的文件归位 |
| [.gitignore](../../.gitignore)忽略本地目录，而[.gitattributes](../../.gitattributes)还包含部分 `agent/local/artifacts/` 的LFS规则 | “本地目录”不天然等于不会公开；历史资产消费者可能仍依赖旧路径 | 以实际跟踪状态和消费者核对为准，不能仅凭忽略规则移动或删除 |
| GitHub为公开仓库，默认分支 `main` 首页声明完整项目版本为 `9dd2873c`，实现保留在工作分支 | 默认首页和本地当前开发内容不是同一份实现 | 展示版本与开发版本分别标识；所有跨版本入口必须落到可访问的完整版本 |

远程事实来源：[GitHub默认首页](https://github.com/JunyeFu/Emotional-Healing-System/blob/main/README.md)，核查于2026-10-13。本地核查基线为 `codex/td-workbench-readability` / `c27ca0d6`，当时存在T-01未提交改动；不得把这些候选文件默认为可发布成果。

### 3.1 GitHub首页内容顺序

1. **项目是什么**：项目名、一句话定义、适用人群和当前阶段。先介绍体验，不先讲目录治理。
2. **可看实物**：一张真实现有画面及成果入口。对“成员演示、设计稿、模拟流截图、实际运行截图”逐项准确标注；没有对应实物就不放占位成品图。
3. **核心设计与系统关系**：简述四天气、A/B完整方案，以及“设备 → Python → Unity/TD → 记录与分析”；详细设计链接出去。
4. **按目的开始**：了解项目、查看成果、继续开发、领取/审阅任务四个直接入口。
5. **当前进度和范围**：保留现有生成进度区块与SVG；同时用短句区分软件模块签收、设计候选和真实验证缺口。
6. **版本与协作**：完整项目版本、当前开发入口和贡献规则。历史迁移过程移到现有工作记录，不继续累积在首页。

首页正文目标不超过150行，首次出现“按目的开始”之前不堆放逐任务清单；不依靠折叠块隐藏理解项目必需的信息。不建设额外展示网站、门户框架或新的文档发布流水线。

### 3.2 开发者应拿到的内容

`human/developers/README.md`承担操作导航，不复制模块实现说明：

- **环境选择**：从现有[Python依赖入口](../../agent/modules/requirements.txt)及[直接依赖基线](../../agent/modules/requirements-baseline-py3.14.txt)配置隔离环境；Unity实际工程版本和团队目标版本分开，TD版本按实际验证结果说明。先检查现有依赖与环境，不自动全局安装或升级。
- **两条路径**：无设备的源码/合同验证；具备Unity、TD或设备时的专项开发。正式研究启动不包装成普通开发命令。
- **模块矩阵**：对每个模块列职责、源码目录、当前任务交接、环境/输入前提、验证入口；直接链接现有内容，不再生成第二套模块编号。
- **首个可执行动作**：至少给出一条已在目标环境实际通过的无硬件定向测试，以及工作目录、预期成功输出和生成文件位置。
- **改动流向**：共享行为改源码权威；任务工具保留执行目录；证据写任务证据目录；生成的审阅文档从源更新。不能只修改PDF，也不能从任务包输入快照反向覆盖源码。
- **下一项工作**：链接当前可领取任务和模块交接。当前缺口留在对应交接中，不在新指南重复维护71项状态。

下列仅是后续上手验证候选，执行者须实际运行后填写结果；本轮任务书编制没有执行它们：

```powershell
# 从仓库根执行；python须指向已配置的隔离环境。
python -m pytest agent/modules/tests/session_core/test_core.py -q
python -m pytest agent/modules/tests/session_store/test_recording_replay.py -q
```

传输、TD和Unity联调涉及端口时，先遵守 `D:\Agent\全局端口注册表.md`；文档测试不得占用正在使用的会话端口。没有统一运行入口时，明确写出各组件入口和未连接部分，不为目录任务另造一套运行框架。

### 3.3 本地文件归属

| 文件类型 | 长期权威位置 | 本地/GitHub处理 |
|---|---|---|
| 介绍与开发指南 | `human/project/`、`human/developers/` | 可公开的Markdown随源码版本维护 |
| 当前程序和原生工程 | `agent/modules/` | 路径先保留；Unity不拆开Assets、Packages、ProjectSettings，不改变资产GUID |
| 任务专用构建/验证工具 | `agent/tasks/<ID>/execution/` | 有明确消费者即可保留；并非所有Python文件都要搬到modules |
| 当前设计与运行协议 | `agent/design/`、`agent/modules/communication/` | 保留单一源，导航只引用；设计候选与运行协议不互相替代 |
| 任务总结和证据 | 现有 `outputs/`、`evidence/`；审阅输出在 `human/tasks/` | 按现有生成方式更新；历史签收与冻结快照保持原件 |
| 展示资产 | `human/assets/` | 只精选当前介绍需要的素材，不复制整个证据目录；来源、许可和范围确认后才发布 |
| 交付制品 | `human/deliverables/` | README列当前入口及历史版本；大制品沿用已确定的LFS/发布方式，不重复存多份 |
| 本机环境、缓存和临时输出 | `agent/local/`或工具已有忽略目录 | 新增Python环境可放 `agent/local/venvs/srp/`；现有可用环境不强制迁移 |
| 工作树与本机历史备份 | `agent/local/worktrees/`、`agent/archive/local/` | 保留使用中的工作树；不创建Agent顶层平行项目 |
| 真实会话、个人信息及密钥 | 当前受控数据配置所指定位置 | 不并入展示资产或开发示例；本任务不迁移真实数据存储 |

不能把 `agent/`理解为“仅AI可读”，也不能把 `human/`理解为“所有内容都能公开”。文件角色、实际Git跟踪状态与发布权限分别判断。

## 四、文件去留与修改边界

| 当前文件/目录 | 目标处理 | 约束 |
|---|---|---|
| 根 `README.md` | 重写内容顺序，保留项目事实和进度生成标记 | 不将历史测试数量作为当前测试结果；不手改生成状态 |
| `human/README.md` | 改为人类阅读导航 | 原任务表移至 `human/tasks/README.md`，不丢失逐包链接 |
| `agent/tools/build_task_reviews.py` | 配套调整上述索引的生成目标与链接相对路径 | 先检查源代码；保留现有逐包LaTeX/PDF路径，验证重生成不覆盖新导航 |
| `human/project/README.md` | 作为项目概览，减少流水账，链接当前设计和真实成果 | 本任务书保留为改造设计依据；修正会误导读者的旧入口名称 |
| `human/project/PROJECT_MODULES.md` 与 `agent/modules/README.md` | 统一模块编号与职责；源码入口以当前实现为先 | 协议版本以实际合同为准，不全局把旧版本字符串替换为新版本 |
| `human/developers/README.md`、`CONTRIBUTING.md` | 新增开发上手和短协作规则 | 操作步骤集中在开发指南，协作规则不复制AGENTS全文 |
| `agent/README.md`、`agent/runtime/README.md` | 明确权威位置、真实运行入口与验证方式 | 不把任务说明当可运行程序 |
| `human/deliverables/README.md`、`human/assets/` | 增加当前成果目录与精选展示资产 | 旧版有使用者就保留入口；本轮不重做全部图片或所有PDF |
| `agent/tasks/*/execution/` | 首先分类；共享运行代码仅在确认错放且迁移有收益时归位 | 必须有逐文件清单、调用者更新和定向测试；不得复制出两套实现 |
| 旧 `main.py`、`visualizer.py`、相关README | 首先从当前启动路径降级到清楚标注的历史入口 | 物理归档前检查仍在使用的测试、引用、任务与演示；不能仅因“旧”而删除 |
| `agent/tools/`中的一次性迁移脚本 | 有当前消费者则保留；无消费者者列入归档清单 | 本阶段不自动批量执行迁移脚本 |
| `agent/governance/`、领取输入、历史签署及证据 | 保持路径和内容；增加短导航即可 | 不重新生成历史签收，不静默改领取快照 |
| `agent/root-layout.json`、Git属性与测试配置 | 只有实际文件归位影响到它们时做最小更新 | 不为导航改造虚报新一轮根目录迁移完成 |

“有限归位”不是开放式清理授权。执行阶段先列出当前路径、目标路径、消费者及验证项；未进入批准清单的文件不搬动。对仍有消费者的历史材料，可以只降级导航而不迁移。

## 五、实施工作包

以下五步属于同一个仓库组织任务，不改变业务任务注册表。建议一名仓库维护者执行、一名未参与改造的成员走查；Unity/TD路径如需变动，由对应模块维护者共同确认。

### W1：确认入口与文件归属

**输入**：本任务书、当前分支和默认首页、模块地图、现有生成器及根目录迁移清单。

**执行**：核对当前可展示版本、可执行入口、任务表生成方式；对拟处理文件形成一张简短表，标明保留、重写、新增或归档。不扫描和整理无关缓存，不改业务内容。

**交付**：批准的目标树、有限归位清单、四类读者的入口草图，记录在本任务的执行目录中。

**验收**：每个将改动的对象都有消费者与目标；没有“整理全部文件”等不封顶项目；明确当前版本与历史快照不能混用。负责人确认清单后才进行物理迁移。

### W2：完成项目展示入口

**输入**：W1清单、当前设计概览、可公开的真实素材、现有任务进度生成区块。

**执行**：按3.1重写根首页和人类入口；精选一项真实展示素材；完善成果目录。首页不给内部日志和全部任务编号占首屏。

**交付**：根README、人类阅读导航、项目概览、成果目录及必要展示资产。

**验收**：访问者能回答“是什么、看什么、做到哪”；四个主要入口可达；图片来源和证明范围明确；保留当前研究边界，不凭目录整理宣称产品完成。

### W3：完成开发和任务入口

**输入**：W1确认的源码与工具路径、依赖文件、实际模块合同及任务索引生成器。

**执行**：补齐开发指南和协作说明；修正Unity/TD编号冲突；将旧模拟启动降级；调整任务表生成目标；实际执行一条无硬件定向验证，写出预期输出及产物位置。

**交付**：开发指南、模块源码导航、运行操作入口、任务审阅索引及其必要生成器改动。

**验收**：新人无需翻历史日志即可找到源码和验证入口；重生成相关索引后新导航不被覆盖，逐包文档路径不变；依赖说明与实际命令相符。

### W4：按清单有限归位并验证
