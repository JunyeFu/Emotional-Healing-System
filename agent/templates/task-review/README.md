# 通用中文逐包任务总结模板

## 当前通用任务入口

领取、执行、验收和交接使用 `human/templates/通用中文逐包任务模板_v4.0.docx`；正式Word模板为同名 `.dotx`。生成脚本为 `build_common_template_v4.py`，依赖 python-docx 与 lxml，不依赖 SRP 业务代码。模板中的项目、领域、工具、目录与人员均为可替换字段。适用于科研、开发、建模、课程和投资研究；v4按四阶段排版，旧版保留为历史参考。

一包一份，启动时填写目标、验收、负责人、上游和执行步骤；过程中更新真实交付；结束时补验证、交接和任务要求的签收。同一负责人对闭环负责，Agent作为实施或复核方单独记录。研究、建模和投资字段按需填写，小任务可压缩为一页，不强制添加独立复核或其他额外流程。

在Word中将占位文字替换为实际内容；文件与资料入口使用“插入链接”填写。采用项目既有状态，不创建并行注册表。当前事实先更新执行权威，再更新Word；历史版本与本次结果分开。

跨项目复用时，只替换项目与任务字段，不沿用其他项目的软件版本、责任人或结论。启动前确定验收标准，收尾时回填同一验收项的实际结果；Agent实施或复核职责与真实负责人分开。领域补充只选本任务适用内容，小任务删除空表和非必需环节，不为了套模板扩充工作。

2026-09-29补齐本次审阅请求、主线作用与反向检查、实际工具版本、下游接收确认。通用模板没有预填项目结果、人员签名、软件版本或教学网址；实际任务包填入已核实的直达链接。使用`.dotx`新建任务文档，使用`.docx`查看或直接填写；两者正文一致。

以下旧总结模板说明仅用于已采用该结构的任务报告，不覆盖上面的新任务入口。

适用科研、编程、设计、建模和项目管理任务。人类阅读Word，Agent维护结构化事实与来源；任务完成时生成总结，并按任务编号串联到项目审阅。

模板为 `human/templates/通用中文逐包任务总结模板.docx`，生成脚本为本目录的 `build_template.py`，可以连同生成的Word用于其他项目，不依赖SRP代码。

模板v1.1按三部分组织：先看结论、启动要求与交付；再看分步执行、验证与问题修复；最后看上下游、责任签收及下一包。实际页数随内容扩展，空项写不适用及理由。

启动时先填任务领域、责任人、目标、验收、上游输入、预计工作量和必需技能，安排每一步的产出与检查；执行中更新实际进展；收尾时填写真实交付、验证、签收与下游接收条件。同一份文件贯穿任务，不另建重复的启动报告。

## 填写规则

- 写实际结果与真实文件位置，禁止用计划文字替代完成结果。
- 工程实现、验证、独立复核、真实第二人签收、实际活动和发布分别按事实填写，不因前项完成自动推定后项。
- 问题先在Agent权威文件中修复，再更新Word；Word不得出现只在文档里修复的完成声明。
- 当前执行文件保持单一明确版本，过期文件写清删除或归档决定；合同、签署、来源原件不按名称旧直接删除。
- 只有任务书明确要求或当前问题需要时才填写提交哈希、锁定证据和其他追踪字段，不追加无消费者台账。
- 签收姓名与日期只使用真实签收信息；没有签收时填写待签收，不预填PASS。
- 学习资料填写可点击链接，中文教学优先；工具版本来自项目环境基线，不在通用模板中写死Unity、TD或其他项目专用版本。
- 科研任务单独说明本包对研究问题或论文主张的作用；工程通过不自动支持实证结论。非科研任务不强填论文内容。

本项目统一使用 `human/tasks/<任务编号>/summary.docx`，串联文档为 `human/project-review.docx`，避免两套命名同时存在。跨项目单文件交付可命名为 `<任务编号>_任务总结.docx`。修订历史保存在Agent层，当前人类入口只展示当前文件。

## Agent层固定结构

`TASK.md`说明范围、步骤与验收；`inputs/`保存输入引用或任务要求的快照；`execution/`保存运行脚本；`evidence/`保存真实结果与复核；`outputs/`保存结构化总结；`archive/`仅保存有保留理由的历史材料。共享实现代码由模块维护，任务包引用权威路径。

## 跨包审阅

按先后任务比较下游所需输入与上游实际输出；检查缺失内容、范围变化、责任人缺口、过期结论和当前项目方向。每个已发现偏离须填写修复位置、复测结果、影响下游和当前处置状态。
