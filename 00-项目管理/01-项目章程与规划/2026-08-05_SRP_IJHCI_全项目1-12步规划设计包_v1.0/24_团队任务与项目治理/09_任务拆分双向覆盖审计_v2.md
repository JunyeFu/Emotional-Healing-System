# SRP任务拆分双向覆盖审计 v2

> 审计日期：2026-08-06
> 结论：原37个固定任务包适合启动工程，但不足以组成规划中的项目完整体。v2改为48个固定任务包和3个可重复批次模板。

## 1. 审计方法

### 正向审计

从每个无依赖任务出发，检查其输出是否经明确依赖进入纵向实现、集成候选、技术预试、正式阶段、锁定分析、论文和成果交接。没有下游消费者的任务视为孤立产出。

### 反向审计

从最终完整体反推以下不可缺少的成果，再确认每项都有任务、输入、过程、客观验收和证据：

1. Unity独立完成四场景与抽象条件的完整参与者体验；
2. 两台真实设备、Python权威会话、在线交互状态估计、不可变记录和重放；
3. TD只读操作台；
4. Level A/B/C、两个正式阶段、阶段二冻结策略和三重证据门；
5. 数据治理、许可、预注册、构建锁定和偏离记录；
6. 自动图表、完整分析报告、单篇IJHCI稿件、投稿包、复现包和成果交接。

## 2. 原37包的缺口

| 缺口 | 原设计问题 | v2处理 |
|---|---|---|
| M10没有实际任务 | `Z-01`只负责构建，不能产出论文、投稿包和成果交接 | 新增`W-01`至`W-04` |
| 正式结果没有锁定报告任务 | `A-02/A-03`偏向工具实现，不能替代阶段一和最终锁定分析 | 新增`A-05`与`A-04` |
| 预注册和版本锁定无人承担 | 外部门禁写在文档中，但没有可领取任务 | 新增`G-03`与`G-04` |
| 数据与资产权限分散 | 真机记录、问卷、Unity素材和公开顺序缺少统一台账 | 新增`G-01`与`G-02` |
| Unity缺少横向成品门 | 五个适配器分别通过不代表视听、分辨率、性能和自动流程整体一致 | 新增`U-08` |
| 大样本任务不碎片化 | 48至240人的执行不可能由单个5人日包真实完成 | 新增`B-01`至`B-03`可重复批次模板；`E-03/E-04/E-06`改为批次关闭任务 |
| 多数任务没有完整过程 | W2至W4只有一行验收摘要，领取者无法判断先后步骤和证据位置 | v2为每包绑定四段过程配置、三条以上验收和证据路径 |
| 任务名领域不清晰 | `F/P/U/...`需要读者猜测领域 | 所有标题增加`【领域】`前缀，并保留稳定ID |
| 学习入口缺失 | 新成员不知道补齐技能的最短路径 | 每包绑定已核验的国内中文学习资料编号 |

## 3. v2规模裁定

### 全部登记项按波次：51条

- W0基础合同：4个；
- W1公共骨架与治理：8个；
- W2纵向实现：15个；
- W3集成、分析和研究工具：8个；
- W4外部门禁与技术预试关闭：5个；
- W5正式阶段、锁定分析和策略冻结：8个（其中2个可重复模板）；
- W6论文、投稿和成果交接：3个。

其中固定任务包48个，可重复批次模板3个：

- `B-01`：Level C会话批次，每实例最多12人、1至5人日；
- `B-02`：阶段一正式会话批次，每实例最多12人、1至5人日；
- `B-03`：阶段三正式会话批次，每实例最多12人、1至5人日。

模板本身不因完成一个实例而标记`DONE`。关闭任务必须核对全部实例、目标样本、顺序/条件平衡、偏离与数据校验和。

## 5. 正向装配门

```text
W0 合同/测量/Unity/TD骨架
 -> W1 Python会话/记录/传输/治理
 -> W2 设备/估计/五种Unity适配/分析基础
 -> W3 无TD真机E2E/研究工具/随机化/策略工具/复现候选
 -> W4 Level A/B/C与阶段一预注册锁定
 -> W5 阶段一批次与Gate1/2/策略冻结/阶段三批次与最终分析
 -> W6 论文稿件/投稿复现包/成果交接
```

每一波必须消费上一波的版本化输出。`07_validate_task_packages.py`验证依赖无环、任务可达最终交接、标题领域、过程配置、学习资料、验收条款和证据字段；它不能替代真实设备、人工复核或外部阶段证据。

## 6. 合理性结论

原37包的工程模块划分方向正确，Python、Unity、TD、设备和离线分析的主要seam也合理；问题不在前半段，而在后半段被过度压缩。v2不拆碎模块内部实现细节，保留深模块接口，同时把跨角色交接、批次执行和最终成果补成可验收任务。因此51条登记项比37个固定包更符合四人团队、单次领取1至5人日和最终项目完整体三个约束。
