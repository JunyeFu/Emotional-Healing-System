# V-04 节点23：大型预演制品存储、提交与分发

> 状态：ACCEPTED
> 日期：2026-08-24
> 当前边界：分发方案已冻结；尚未创建Release、标签或大型候选附件。

## 1. 决策

V-04采用“本地隔离大型工作制品、普通Git保存权威源和清单、GitHub预发布分发冻结候选附件”的方式。本轮不配置Git LFS。

GitHub普通Git阻止超过100 MiB的单文件，参考[GitHub大文件说明](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github)。Git LFS对每个新文件版本计量存储和下载带宽，参考[Git LFS计费说明](https://docs.github.com/en/billing/concepts/product-billing/git-lfs)。GitHub Release允许最多1000个附件、每个附件小于2 GiB且不限制Release总大小，参考[GitHub Release说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。

## 3. 普通Git内容边界

普通Git保存：

```text
分镜JSON与Schema
确定性设计预演轨迹
渲染与验证脚本
工具锁
资产与声音清单
提示词与来源记录
分镜缩略图或联系表
时序CSV与Markdown
媒体和差异掩码报告
artifact_manifest.json
candidate_release.json
复核与审核报告
```

普通Git禁止完整MP4、完整WAV、FFmpeg二进制、渲染缓存、逐帧图片序列、大型临时PNG和ZIP候选包。单文件达到25 MiB时告警，达到50 MiB时验证失败。

## 4. 候选分包

```text
V04_participant_views_<candidate_id>.zip
V04_review_views_<candidate_id>.zip
V04_audio_masters_<candidate_id>.zip
V04_source_assets_part01_<candidate_id>.zip
V04_source_assets_part02_<candidate_id>.zip
V04_evidence_<candidate_id>.zip
V04_SHA256SUMS_<candidate_id>.txt
```

- 每个附件目标小于1.5 GiB，硬上限2 GiB。
- ZIP使用固定文件顺序、固定时间戳和固定压缩参数。
- 同一媒体不重复进入多个ZIP。
- ZIP及内部文件都记录SHA-256。
- 源资产超限时按资产ID稳定分片，不按临时目录随意切分。

## 5. GitHub预发布身份

```text
tag=v04-design-preview-candidate-1.0.0
title=V-04 Design Preview Candidate 1.0.0
type=PRERELEASE
identity=V04-DESIGN-PREVIEW-<candidate_commit_sha>
```

预发布不标记`Latest`。说明必须包含：

```text
DESIGN_PREVIEW_ONLY
TEMP_REFERENCE_ONLY
REVIEW_REFERENCE_ONLY
NOT_UNITY_RUNTIME_EVIDENCE
NOT_FORMAL_BUILD
NOT_FORMAL_ASSET_CLEARANCE
```

## 6. 候选清单

仓库内`candidate_release.json`至少记录：

```json
{
  "candidate_id": "V04-DESIGN-PREVIEW-<sha>",
  "candidate_commit": "<full_git_sha>",
  "release_tag": "v04-design-preview-candidate-1.0.0",
  "release_url": "<github_release_url>",
  "release_status": "PRERELEASE",
  "artifacts": [
    {
      "name": "V04_participant_views_<candidate_id>.zip",
      "size_bytes": 0,
      "sha256": "<sha256>",
      "github_asset_id": null
    }
  ],
  "evidence_scope": "V04_DESIGN_PREVIEW_ONLY",
  "formal_use_allowed": false
}
```

上传后将附件ID、下载地址和远端大小写回清单，形成单独治理提交。

## 7. 不可变性

- Release标签与候选提交必须一致。
- 进入独立复核后不得替换同名附件。
- 附件变化必须生成新`candidate_id`和新预发布版本。
- 不允许替换视频却保留旧清单哈希。
- 第二人审核同时绑定Git提交SHA和候选清单SHA。
- V-04签收后保留原预发布，不把它改写成正式Unity版本。
- U-03/U-08使用新的发布身份，不复用V-04标签。

## 8. Git LFS边界

本轮不修改`.gitattributes`，不使用Git LFS上传V-04媒体。只有团队明确需要大型源资产随分支版本化、已核对额度预算、已定义清理归档和协作规则并经第二人批准后，才另开仓库级治理决策。

## 9. 上传失败处理

- 上传失败不得把ZIP转提交普通Git。
- 单文件超过2 GiB时按稳定资产ID重新分片。
- 网络中断使用同一文件和SHA-256重传。
- 远端大小或下载哈希不一致时标记`UPLOAD_INTEGRITY_FAILED`。
- 远端未完成前不得进入独立复核。
- 不自动删除本地候选。

## 10. 验收要求

1. `.artifacts-local/`已被Git忽略。
2. 普通Git不存在完整MP4、WAV、ZIP或FFmpeg二进制。
3. 普通Git单文件均低于50 MiB。
4. 每个Release附件低于2 GiB，目标低于1.5 GiB。
5. 本地、ZIP内部和远端下载哈希一致。
6. Release标签指向候选提交。
7. Release为`PRERELEASE`且不标记`Latest`。
8. Release说明包含六项证据边界。
9. 仓库清单可定位所有附件和GitHub附件ID。
10. 独立复核对象同时绑定Git提交和候选清单。
11. 附件变化产生新候选版本，不覆盖旧候选。
12. 本轮不新增Git LFS规则。
13. 远端分发成功不扩大为Unity运行或正式构建完成。
